# Agent Guide — gnockpit

## What is this?

gnockpit is a real-time monitoring dashboard for gno.land validator nodes. It's a single Go binary (`gnockpit [flags]`, no subcommands) that connects to one or more gnoland RPC endpoints (`-rpc`, repeatable), consolidates their views, and serves a live web dashboard, with web-push/PWA alerts and external (Shoutrrr) notifications.

## Key Concepts

### Data Flow

1. `server.go` runs a **publish loop** every N seconds (default 5s)
2. Each cycle calls `fetchSnapshot()` which polls every configured source (`node/sources.go: Poll`): global chain data (status, validators, consensus, signing) comes from the freshest reachable source; peers are unioned across all reachable sources and deduped by node ID (`MergePeers`) before their RPCs are probed. All sources down → `snap.Error` drives the "connecting to sources" banner.
   The publish loop also rereads the notification config file when it changed, and, once the snapshot is set, sends the lead-time alerts (`notifySchedule` → `push.Manager.EvaluateSchedule`: a new halt, once per device or target, and its approach, once per device and once per lead of a target, recorded in `push_sent`; the reminders whose lead is met, then dropped, their device kept). Every push or webhook send is bounded by `--send-timeout`.
3. The snapshot is broadcast to every WebSocket client as one `update` message (see WebSocket protocol)
4. `web/js/live.js` handles each message in one pass and updates the DOM in place; the tables, cards and map redraw only when what they show changed
5. Each cycle also geolocates peers (`geoip`) and resolves their cloud provider (`asn`) — using each peer's resolved public IP only (peers with no usable public IP are geolocated to nothing and bucketed "Unknown" on the map) — and refreshes the missed-24h counts and the 24 h proposals expected / missed from the `blocks` store (#7, `refreshMissed`). This powers the network map and the Country/Provider columns. Validators inherit the country/provider of their correlated peer (matched via `ValAddress`), so validators no source is peered with have none.
6. Separately, `eta.Tracker` (started in `main.go`) runs its own loop on the primary source: every minute, and back to back while backfilling, it reads the chain head, drops the stored history if the chain id changed, reads the halt params, and fetches the missing every-100th block times newest-first. `/api/eta` combines its model with the snapshot's newest block; the dashboard's ETA cards poll `/api/eta` every 10 s and tick the countdown locally in between. The link card's target lives in the page link (`?eta=&since=&label=`), or in the device's reminder (`push_reminders`) for a page opened without one; the halt card's comes from the chain params; the "original" estimate is recomputed from the stored history as of `since`.
7. Separately, `blocks.Tracker` (started in `main.go`) fills the block history from the primary source. Deltas worth knowing:
    - Each pass: heights up to head − 1 (the head's commit is final only once the next block carries it), then one batch below the stored range; `--history-pace` between batches while backfilling or catching up, 5 s once complete. A non-canonical commit, or a commit refused within 1,000 blocks of the head (a lagging backend), ends that direction quietly; logged after 2 minutes. A short batch timing out ends the pass.
    - Floor: set when two answers serve a height and refuse the one below, over 1,000 below the head (a downward batch of 2+ calls opens with the lowest stored height as that witness). A refusal first in its answer (the witness, or a batch of 1) sets no floor; twice in a row at one height, over 1,000 below the head, it pauses the backfill for 10 minutes, logged once; a served downward answer resets it. So a batch of 1 (flag, or a source taking 1 call a batch) never completes at a floor: it pauses there. `floor−1` is rechecked after the head at each start until an answer settles it (served clears the floor), never failing a pass.
    - A batch refused whole halves `--history-batch`, rounding up (2 comes before 1), until restart; one timing out, for 10 minutes. HTTP 429 waits `Retry-After` on every read.
    - Set changes: `Write` records a height whose set differs from the stored height below (settling the written height and the one above, so a batch edge is caught either way). After the upward loop, the tracker tells (`OnValsetChange`, wired to `push.Manager.NotifyValsetChange` in main.go) the changes above the `valset_told_to` watermark, which starts at the first stored high: the backfill and a new chain's first fill never tell.
    - `/validators` once per new `validators_hash`, plus h−1 and h for a block with round > 0 (rounds kept) and every 1,000th (check only); a set below refused twice, over 1,000 below the head, flags the block; a first refusal, or one nearer, fails the pass. Set-change events from `/block_results` at H−2; a failed read becomes an event gap, retried every 10 minutes, dropped when its events are below the floor.
8. Separately, with `--ranking`, `ranking.Publisher` (started in `main.go`) runs a pass every 30 s: it serves `Readiness` (from the block tracker's `Progress`, read from the store when the tracker is built, so a restart's first pass sees the stored history) and the chain's latest stored day. Once ready, with the chain id known, every valoper profile the realm lists read (`Server.Valopers` whole) and today's first block stored, it publishes today's ranking into `ranking_days`, each history read as the window ends (`WindowHistory`: blocks stored later change no history; keys are linked by every stored event and the current profiles, so a later event or profile can change a link, and with it a score), and tells `OnPublish`, wired to `push.Manager.NotifyRanking` (once per target and `chain:day`). Today's served day with the same formula and exclusion list is not recomputed.

### Validator history (blocks/history.go, web/validator.go)

- **Counters**, kept by `Write` with each record: `blocks_days` (day, validator → absent, nil_votes, other_block, proposals_expected, proposals_missed), `blocks_gaps` (b where block b+1's time is over `RestartGap` after b's) and `blocks_absence_runs` (validator, first, last). Each is filled once for blocks stored before it, while its meta key (`days_filled`, `proposals_filled`, `gaps_filled`, `runs_filled`) is unset; `Reset` sets them all.
- **Blocks in the set** are derived, never stored: `blocks_vote_delays.votes` (one per precommit present, nil and other block included) + absent.
- **Proposals**: k = the earliest round ≤ the commit round whose expected proposer is the header's; rounds 0..k expected, 0..k−1 missed. Unknown rounds or no match → the height counts nothing. `blocks_days` counts every height; `Summary.ProposalsExpected` / `ProposalsMissed`, the scoring's, count only the heights the validator signed, restart heights b left out.
- **Recovery** after a restart at b, judged on the validator's runs merged across its keys, one of its keys in the set at b−1 and one at b: R = the run holding b, else the one ending at b−1; h = R.Last+1 when R holds b, else b; a sample when fewer than 10 of R's heights are ≤ b−1, R does not start at the stored low (above 1), and one of its keys is in the set at h (else none); pending while block h+1 is not stored (for the ranking, `WindowHistory`: while it is above the window's last height + 1); duration = time(h+1) − time(b+1). Every sampled R is a recovery run, the one ending at b−1 before a signed b included. The last 3 samples of the 180-day span are `Scored`.
- **Outages**: runs of 10+ absences (absent or other block; a key's run and the next key's starting right after it, a rotation, are one), recovery runs left out up to 24 h of block time after block b+1 (past that, the rest when it holds 10+).
- **Scoring constants**, NEVER behind a flag (a change to any bumps `ranking.FormulaVersion`, which names them): `OutageMin`, `recoveryRunCap`, `scoringDays` (30 complete UTC days before today), `recoveryDays` (180), `recoveryLast` (3) in history.go; `RestartGap` in gaps.go; the weights, mappings and 168 h minimum in ranking/rank.go.
- **Identity**: `OperatorKeys` reads an operator's spans from set events (Added at H opens a key from H, or from 0 when the stored set at H−1 holds it: a power change, which keeps an open span; an applied rotation at H closes the old key at H−1 and opens the new one at H; Removed closes at H−1), plus the profile's key when no event names it. `/api/validator` resolves `?val=` to the operator it is, else `OperatorOf` (an event naming it), else a profile naming it as signing key, else the key alone (operator "") when `Known` or in the current set; else 404.
- **Valopers**: `valoperRefreshLoop` (every 15 min) → `refreshValopers` reads every profile's render and two `vm/qeval` reads (`KeepRunning`, `LastRotationHeight`) into `Server.valopers`, keyed by the operator the registry lists. A failed state read leaves `State` nil; a failed or unparsable render keeps the operator's last profile, and a list read in part or not at all keeps every last profile; each logged once a refresh, the unread operators named. `Server.Valopers` is whole only when the last refresh read the whole list and every operator it lists has a profile, from it or an earlier one: the ranking waits for it.

### NameRegistry (validators.go)

Maps validator addresses to human-readable monikers. This is critical because Tendermint RPC only returns addresses, not names. Discovery happens through:

- **Genesis (RPC)** — validator names and the genesis time are seeded at startup by streaming the node's `/genesis` endpoint, parsing only the head (the large `app_state` is never downloaded)
- **Peer RPC queries** — when we query a peer's `/status`, we get their validator_info.address + moniker
- **Node-ID verification** — on shared IPs (multiple nodes same IP), the RPC response's node_info.id is checked against the peer's P2P node-id before trusting the mapping
- **Correlation** — unmatched validators are matched to unmatched peers heuristically

The registry persists to a JSON file (`--names` flag) so discoveries survive restarts.

### Signing Stats (client.go: GetSigningStats)

Fetches the last N blocks (default 100), extracts:

- Who signed each block (from `/commit`'s precommits, which finalize that height; one for the block or for nil signs it, an empty slot or one for another block misses it, as in the block history)
- Who proposed each block (from `header.proposer_address`)
- Block timestamps → the chain-wide average block time
- Per validator: missed (absent, or a precommit for another block), nil votes (signed), and the median delay of its precommits from each commit's median time (below), within the blocks it was in the set for

This is a live 100-block window; the commits the node marks `canonical` (final)
are kept in memory, so a refresh fetches only the heights not yet read final:
one or two when the window slid by one block. A precommit's delay is from block h+1's header time (tm2's weighted median of commit h), the newest commit's from `MedianTime`. Longer-term **missed-block counts** come from the
`blocks` store (Data Flow #7) via `MissedByWindows`.

### HTTP API (CORS-open JSON)

- `/api/status` (status.go) — health summary (retrocompat `status`/`chain`/`height`/`reason`/`time`) plus `network`, `recent_blocks` (last 100), and per-`peers`/`validators` column data.
- `/api/stats` (stats.go) — per-validator missed-block windows, provider + country aggregates, validator-set health, Nakamoto coefficient.
- `/api/eta` (eta.go) — `?height=` (+`since` for original/drift/trail), `?time=`, or none for the on-chain halt.
- `/api/history` (history.go) — the block history's reach (`filled`); `?from=&to=` (≤ 1,000 heights): blocks with absent / nil / other-block members, round proposers, flags, set changes, and the validator sets; `?days=N` (≤ 31): daily vote-delay histograms; `?changes=N&before=H` (≤ 100): set changes newest first with their diff, paged by `next_before`.
- `/api/validator` (validator.go, validator_timeline.go) — `?val=<g1 operator or signing key>`: status, keys, moniker, location, profile, timeline (with `recovering` for a pending recovery), vote-delay edges, days, recoveries (`scored`), summary, live; 400 malformed, 404 unknown, 503 history off (unreachable in the shipped binary: main always sets the history up). Not paged.
- `/api/ranking` (ranking.go) — `GET` only (405); 404 while `--ranking` is off; `state` (readiness), `hide_excluded`, `ranking` (the latest published day, null until one is). `/api/boot`'s `ranking` tells the page whether to offer the view.
- `/api` (server.go) — raw `Snapshot` dump (unstable shape; debugging).
- Also: `/badge.svg`, `/ws`, `/api/boot`, `/api/links` (links.go: the header links and each status link's state, which the page reads every 30 s), `/api/push/*` (subscribe: one device per endpoint, `""` id once it has nothing left, `keep` the alert types whose stored alerts a save leaves, as the page sends for the validator alerts while it cannot read the validators; `shown` the validators the menu listed, the device's alerts on any other staying unless the save names it; entities 503 while no consensus state is read; `/api/push/reminder` in reminder.go), `/api/notify/*` (the config's targets and their alerts, a test send; `GNOCKPIT_NOTIFY_TEST_TOKEN`).

## Important Patterns

### No hardcoded values

Everything chain-specific is auto-detected or configurable via flags; the scoring constants are fixed in code on purpose (Validator history). The tool works on any gno.land chain without code changes:

- Chain ID → from RPC `/status`
- Genesis time + validator names → streamed from RPC `/genesis` (head only)
- Validator names → also discovered dynamically from peers

### RPC errors

`rpcGet` returns a `*node.HTTPStatusError` (with `RetryAfter`) for a non-2xx answer; `rpcGetJSON` wraps a `*node.RPCError` for a JSON-RPC `error` envelope, which gno sends with HTTP 200 (e.g. a height out of range). `node.IsRefusal` tells a node refusing a call (JSON-RPC error) from one failing to answer (transport error, HTTP error status). Decode RPC results through `rpcGetJSON` (one call) or `rpcBatch` (a batch: a refusal of the whole batch is a wrapped `*RPCError`, a call's own error is in its answer) so neither passes silently.

### The page: one HTML file, ES modules

`web/index.html` holds the markup and CSS; its script is the ES modules of `web/js/`. No build step, no bundler, no framework, no runtime dependencies; tsc is a check only (`noEmit`). `index.html`, `service-worker.js` and `js/` are embedded via `go:embed`.

Serving: `/js/<file>.js` has `Cache-Control: no-cache` and a content ETag (`static.go`), 405 for methods but GET and HEAD; `index.html` is `no-store`.

The **only** thing that may add an external origin to that page is `--analytics`
(`web/analytics.go`), which splices a provider snippet in just above `</body>` as the page is
served. It is off by default and must stay that way: most gnockpits watch their operator's own
validator, so the default dashboard has to report to nobody. `--analytics-domain` moves that
provider's script and pixel to a custom domain and adds no origin of its own. Keep the page
self-contained otherwise.

Rules for adding code to the page, each ending with what enforces it:

- Put it in the module of its feature; a helper two features use goes in a helper module. New module: add its `import` and `startEach` entry to `main.js` and a `<link rel="modulepreload" href="/js/<file>.js">` to `index.html` (preload: `TestIndexPreloadsEveryModule`; `main.js` and `startEach`: unenforced).
- The top level declares and looks up only. Every side effect (listeners, timers, requests, DOM writes) goes in an exported `start()`, which `main.js` calls through `startEach` (unenforced).
- `main.js` lists the features in the order `startEach` runs them, which is the order their listeners and first draws register: insert a new feature where it must come relative to the others, and never reorder an existing one. A `start` must not rely on another feature having started unless that order guarantees it: eta's reminder awaits `whenPushReady()`, which alerts' `start` sets, so alerts starts before eta (page tests).
- Look up an element the page needs with `$(id)`, `$svg(id)` (an SVG element) or `$in(root, selector)`, which throw naming it; call `document.getElementById` only where its absence is real and handled. Read an index that cannot miss with `present(x)` (tsc, `TestLookupsNameTheMissingElement`).
- State two modules share lives on `live` (`state.js`) and is read and written as `live.<name>`. A module-level `let` another module needs is a defect (unenforced).
- No regex lookbehind, `(?<=` or `(?<!`: Safari before 16.4 cannot parse one, and a module it cannot parse stops every module (`TestJSHasNoLookbehind`).
- No import cycles (`TestModulesFormNoCycle`). No writes to an imported binding: write through `live` or an exported function (tsc).
- Types are JSDoc (tsc). A server answer's typedef goes in `web/types/`, named after its Go type, with its JSON tags (`omitempty` or `omitzero` = optional; a pointer, or a slice the server can leave nil, = nullable). No `any`, no `@ts-ignore` / `@ts-expect-error` (unenforced).
- A wide query negates its narrow one, `not all and (max-width: N)`, never `(min-width: N+1)`, which a fractional width (browser zoom) between the two escapes; JS asks the same query through `matchMedia`, never `innerWidth` (unenforced).
- A default must show as the first paint, before any module runs: a layout in CSS without the class the JS adds, a control's state in the markup (`checked`) (unenforced; `TestPageNetworkCompactBeforeTheScripts` covers the Network State's phone default, `TestPageRecentBlocksCompactBeforeTheScripts` Recent Blocks' compact box).
- `make typecheck` before any commit touching `web/js/` or `web/types/` (tsc).

#### The validators card's views

- `timeline.js` holds the switch (Live, Timeline, Ranking) and the Timeline; `ranking.js` the Ranking view, which `setView` starts and stops through `rankingShown(explain)` / `rankingHidden()`.
- The Ranking button is `hidden` until an `/api/boot` answer says `ranking: true`: `boot.js` calls `offerRanking` on every answer. NEVER infer the ranking from a failing `/api/ranking`.
- The card opens on `?view=live|timeline|ranking`, else the saved `gnockpit-validators-view`, else Live. A Ranking view so chosen (by `?view=` or saved) waits for the first answer saying on, Live showing meanwhile; an answer saying off moves the Ranking view to Live, and the next saying on brings it back, unless the viewer picked a view. `?view=ranking&explain` (the Discord alert's "More info ↗") also opens the "How is this ranked?" dialog, once, when that Ranking view first draws a ranking (`timeline.js` holds the wait until it shows that view, and passes it on, `rankingShown(true)`; `ranking.js` opens the dialog, `openExplainer`, once it has put the ranking on the panel, unless another dialog (`.eta-modal.open`: a validator's page, the alerts, the planner) is open by then, which ends the wait with the dialog closed; a failed read, a state without a ranking or a draw that throws leaves it waiting; the next showing or hiding of the view takes it back, so leaving the Ranking view before its first drawing, the fallback to Live included, or a click on the switch drops the dialog for that page load); `explain` counts only beside `view=ranking`. Once the Ranking view's wait ends, the dialog opened or not, `ranking.js` takes `explain` out of the address (`endExplain`), and, on `popstate`, out of every entry the reader goes back or forward to after (`dropExplain`: a validator page opened during the wait pushes an entry over one holding it), `view=` kept (`history.replaceState(history.state, …)`): the links built from the address (valpage's `urlWith`, the ETA card's copy link) never ask for the dialog again. Only a click on the switch saves a view: never `?view=` (the daily alert links `?view=ranking`), nor a view the card shows on its own. A click also takes `?view=` and `explain` out of the address (`history.replaceState(history.state, …)`, keeping the validator page's entry state), so a reload opens the view clicked.
- The Ranking view reads `/api/ranking` when shown and every 60 s (10 s bound), giving up the read in flight when it hides or reads anew; a click on Ranking while it shows reads anew. An answer equal to the one shown redraws nothing; a redraw gives the keyboard's focus back to its control (`focusPlaceIn` / `focusPlace`: `data-key` on the meta line's controls, the header row, each operator's row and card).
- `ranking-help.js` holds the Ranking view's explanations, which `ranking.js` calls on each draw: the header popovers (on a card, the rank's and the values' labels carry them: `button.info-btn`s, as the table's headers; the page's older ⓘ spans elsewhere stay spans), the value, score, not-ranked-yet and hidden-count popovers (`popRows`; the hidden count a `button.info-btn` too), and the "How is this ranked?" dialog (`#ranking-modal`, the `.eta-modal` parts, opened by `openExplainer`, which hides an open popover first and which one delegated click on `button.rk-how` calls, as does `ranking.js` for `?explain`; closing it focuses `button.rk-how`, or, when the page shows none, as with the Validators section folded, that section's title). The popovers write `/api/ranking`'s figures and counts derived from them (counted blocks, uptime, missed share, the day ranked from), never a score, rounded as the cells. Every scored figure, on the view and on the validator page, is written never better than its value (format.js): an uptime down (`pctDown`), a sub-score down to 3 decimals (`subScoreText`), points down to one decimal and the weight's text only at full marks (`pointsText`; a weight half-up, `weightText`), a score down to one decimal (`scoreText`, as ranking/digest.go writes it), a missed share up (`pctUp`), a recovery time up (`durationUpText`); a band reads the value, never the figure written. The dialog's copy is static in `index.html`; its window, heights and formula fill from the ranking drawn, its curl line from `location.origin`.
- A change to any scoring constant bumps `FormulaVersion` and updates `ranking-help.js` (`WEIGHTS` 50/20/20/10, `MIN_HOURS` 168, its copy), `ranking.js`'s copy (the 180 days of the filling and unavailable lines, the separator's "(7 days)"), `#ranking-modal`'s copy, and README's Ranking section: `/api/ranking` publishes only the weights after redistribution.

### WebSocket protocol

`{type, data}`, two types only: `snapshot` (on connect, once a snapshot exists) and `update` (each publish). Both carry `liveData` (server.go: `buildLiveData`); a new field goes there.

| Field             | Content                                                                                                                                                                                               |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `time`            | the snapshot's fetch time, `15:04:05`, server-local                                                                                                                                                   |
| `status`, `votes` | always present; null while every source is down, `votes` also when the consensus read fails; without `status` the last head stays                                                                     |
| `peers`           | always present; null while every source is down, `[]` when none is seen: the page empties the tables and hides the map either way                                                                     |
| `checks`          | `apphash_last`, `val_address`, `val_pubkey`, `hide_sources`, `system.genesis_time`; `system.node_time` is `s.now()` as the message is built, to the ms (`historyTime`): the page sets its clock by it |
| `signing`         | left out when nil                                                                                                                                                                                     |

`/api`'s dump keeps the fetch's node time, to the second (`collectSystemInfo`).

### Scroll preservation

`renderNodeLists()` (`web/js/node-lists.js`: validators and peers tables and cards) redraws only when `nodeListsFingerprint()` changed; it saves `window.scrollY` and the focused cell or card control before the redraw and restores both after.

### Collapsible sections

`web/js/sections.js`. Each card's `<h2 data-section="name">` holds a `<button>` filling the title that folds the section: `.collapsed` on the h2, `aria-expanded` on the button. Folded keys persist in `localStorage` under `gnockpit-collapsed`, or `gnockpit-collapsed-mobile` when the window was ≤ 768 px wide at load.

## Common Tasks

### Adding a new RPC data source

1. Add the fetch method to `node/client.go`
2. Add types to `node/types.go` (or beside their read, as in `chain.go`)
3. Call it in `web/server.go: fetchSnapshot()`
4. Add it to `liveData` (`web/server.go: buildLiveData`), which both WebSocket messages send
5. Type it in `web/types/server.js` (`LiveData`, or the answer's own typedef) and read it in the `message` listener (`web/js/live.js`)

### Adding a new peer table column

The value comes from a `node.Peer` field (`node/types.go`): the `/ws` `peers` send them all, so a new field needs only filling in `fetchSnapshot` (`web/server.go`). Step 1 edits `web/index.html`; steps 2–7 edit `web/js/node-lists.js`; the `node.Peer` field gets its typedef in `web/types/node.js`.

1. Header, in `#peers-card`'s `<thead>`: `<th data-sort="key"><button type="button" class="info-btn" data-popover="…">Label</button></th>` (a plain `<button type="button">` without a popover, as Name). `sortBy` and `updateSortHeaders` take any `th[data-sort]` (`aria-sort`, the arrow). Add its `<col>` to the `<colgroup>` (widths sum to 100 %) and count it in the loading row's `colspan`.
2. Row: in `renderNodeLists()` (`node-lists.js`), the `otherPeers` loop builds each row (`tr2`): append the cell in column order (`createCell`, or a builder: `peerRPCCell`, `countryCell`, `providerCell`, `midTruncCell`).
3. `emptyRow('no peers', 6)`: the column count.
4. Sort: a `peerSortKey` branch in the `otherPeers.sort` comparator setting `va`/`vb` for `compareSortValues`: `null` for a missing value (last either way); a value shown as a name joins `peersByName` (`compareNames`); a column that shows a code when narrow sorts by what it shows, as Country (`peerCountryShowsCode`, measured before the cells are cleared). Ties keep `setPeers`' name order.
5. Card: in `buildPeersCards()`, a `[label, value]` in `makeCard`'s `data.minimal` `fields` and its property in the peers' `makeCard({…})` call; a `copyLines` line if the card copies it.
6. `nodeListsFingerprint()`: the field in the peers' list, or its changes never redraw.
7. Focus: rows and cards are keyed by `peerKeys()` (node id, else moniker, else IP and rank, else rank), never by the new value; `focusPlaceIn` / `focusPlace` give the focus back to the same cell's control, so a control in the new cell needs nothing more.
8. Tests: `peersCol…`, `peersCardKeys` (`page_peers_helpers_test.go`); in `page_peers_test.go`, `peersKeys` with TestPagePeersTableHead, `peersNetworkRows` with TestPagePeersTableRows, `peersNetworkCards` with TestPagePeersCards, TestPagePeersCardCopy, `peersSortNetwork` with TestPagePeersSort and TestPagePeersSortMissingLast; TestPageTableHeaderPopovers (its popover), TestPageValidatorsEmpty (the column count), TestPageShownValuesFollowTheirData (the fingerprint).

## Testing

```bash
go test ./...
```

Go tests cover the RPC parsing, the stores, the trackers (fake sources) and the HTTP handlers. `go test ./...` needs Node on `PATH`: its node-backed tests (`modules_test.go`, `TestJSSyntax`) run `node`, and fail naming it when it is missing.

`web/push/discord_examples_test.go` (build tag `discord`) sends one example of every alert, with realistic names, then a set change caught up after downtime and, last, an escaping check of hostile names, each announced by a message, to a test Discord webhook. It reads the first `.ignore/dev/discord-test-url` found from the package directory upward (Discord's `https://discord.com/api/webhooks/<id>/<token>` or `https://discordapp.com/api/webhooks/<id>/<token>` URL, or a `discord://` URL used as is; the test skips when none exists) and never prints it. The file holds the webhook's secret, and this repository's `.gitignore` does not list `.ignore/`: keep it out of commits (a global gitignore, or `.git/info/exclude`):

```bash
go test -tags discord -count=1 -run TestDiscordExamples ./web/push/
```

The page tests drive `web/index.html` in Chromium and WebKit against the real server, filled with chain data built in Go. The push tests stub the browser's Push API in an init script (`page_push_test.go`); every other answer comes from the real handlers, and the test server can hold or drop a request on purpose. They need the browsers, installed once:

```bash
make install-browsers
make test-page
```

`make install-browsers BROWSER_INSTALL_FLAGS=` installs the browsers without their system packages (`--with-deps`). `make test-page` runs with `-count=1`: never a cached pass.

CI runs the suite on macOS (`page` job, `macos-26`). NEVER move the `page` job to Linux: Linux's WebKit makes no click of a tap unless an element, not the document, listens to clicks, so the phone profile's tap tests fail there; iPhones and macOS's WebKit turn such a tap into a click.

- A page test MUST NOT depend on font metrics (how many rows fit a box): Linux's fonts fit more than macOS's.
- A page test MUST NOT assume one platform's browser default for a modifier key: branch on `runtime.GOOS` where it differs.

The full page suite takes about 13 minutes on an M4 Pro (23 on CI's macOS runner): from an agent's shell, run it in the background. One test, on one profile:

```bash
go test -tags page -count=1 -run 'TestPageX/desktop' ./web/
```

- Live data: an unknown WebSocket message type: the server sends only `snapshot` and `update`, and a made-up frame would fake the API.
- Network State: the app hash's `-` for a missing hash: the page fills the hash only from a set `apphash_last`.
- Network State sync line: a JSON error answer to a read (`res.ok` false): the history's only JSON error is its 503 when disabled, which never follows a shown line; a proxy's error has no JSON body.
- Network State sync line: stored blocks without `from_time`: the server sets it whenever `from` is above 0.
- Recent Blocks: a missing validator listed by its address alone: the server names an anonymous validator by its address.
- Validators table: a missed count that is not a number: the server always sends both counts as numbers.
- Validators table: Country sorted by country name: its column, narrow on a page at most 1400 px wide, shows and sorts ISO codes.
- Validators and Peers tables: Space on a sort header leaving the page unscrolled (ledger Ruling A-D7 Space, on both tables' sort headers): a native button does not scroll the page, and no test catches a scroll there without a fixed wait.
- Timeline view: a change other than genesis adding, removing, repowering and rotating no member: the set hash covers addresses and powers, so it cannot occur.
- Timeline view: bad JSON in a 200 answer: the server's handlers answer JSON, and a proxy in front answers its errors with their status.
- Ranking view: a draw that throws leaving the dialog closed under `?explain`: it takes an answer that breaks the server's contract, and a hand-made one would fake the API.
- Ranking view: the uptime popover of an entry with no counted block, every block of its window in a recovery run: only an excluded operator joining under 10 blocks before a restart, absent since and within 24 h of it, is one.
- Block ETA: `HTTP <status>` for a non-OK JSON answer without `error`: neither gnockpit nor a proxy in front answers one.
- Block ETA: `still loading` without `back to <day>`: the server sets `history.from` whenever the history is incomplete and has samples.
- Validator page: `could not load` for a JSON error without `error`: every JSON error the server answers carries one.
- Validator page: `could not show it: …` (drawing a report throws): no real report reaches it, and a hand-made one would fake the API.
- Validator page: `openValidator` for the validator the URL already names (no history entry pushed): reached only while a close's `history.back()` is in flight, a race input events cannot time.
- Validator page: the closing page's own hiding of an open popover: the shared popover code hides it first (target hidden, focus leaving, Escape, a click elsewhere), so no test can tell the two apart.
- Validator page: a chart day with `in_set` 0: every stored block counts each member of its set absent or voting, so a stored day has `in_set` ≥ 1.
- Validator page: Timeline entries of an unknown kind: the server sends only its eight kinds.
- Alerts and reminders: the browser's own notification permission prompt: the tests stub the Push API and `Notification.permission`, which headless Chromium reports denied.
- Alerts and reminders: web push in Safari: Playwright's WebKit has no `PushManager`, so push runs on Chromium and the phone checks the buttons stay hidden.
- Reminders: `.eta-remind-pop[hidden]`: it repeats the browser's own `[hidden]` rule, so no test can fail on it.
- Copy: the text WebKit copies: the Global Constraints read the clipboard on Chromium only, so the phone's copies check their toast.
- Every area: presentational CSS (paddings, fonts, gaps, cursors, fixed positions, the planner's 85vh, ellipses, hover-only rules): the suite tests behaviour, not pixels.

## Deployment

Typical systemd service:

```ini
[Service]
ExecStart=/usr/local/bin/gnockpit \
  --rpc http://127.0.0.1:26657 \
  --port 8080 --addr 127.0.0.1 --interval 5s
```

Usually behind a reverse proxy (Caddy/nginx) for TLS.
